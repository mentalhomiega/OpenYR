## Findings that still need a decision

Each needs gamemd evidence or a play test, or touches behaviour the owner has documented as deliberate.

1. `code/reinf.cpp:506`, `Do_Reinforcements`, Droppod branch. When `PDPLANE` is missing or `Send_Plane` returns NULL (`code/house.cpp:10117`: no entry cell, `Create_One_Of` fails, or `Unlimbo` fails), the function returns `true` with the group and its team still in limbo. Nothing frees them and the team never ends. Failing case: a rules file without `PDPLANE`, or a paradrop when the object limit is reached. Fix: delete the chain as `Create_Reinforcement` does (`reinf.cpp:744`) and return `false`. The branch predates `1cb8bf7`; `7741bf3c` only removed the pod link beside it.
2. `code/reinf.cpp:691`, `Create_Reinforcement` retry. A cell that cannot take the member sends the loop to a neighbour that is not `Map.In_Radar` and that `Can_Enter_Cell` accepts. Since `c9e81756` the group is placed on its own cell with no nearby search, so this path is far more reachable: a blocked waypoint cell almost always ends in `delete object`. The `!` looks inverted, and the `continue` may step between cells without end. Fix: test `In_Radar` without the negation, and count the steps. This needs gamemd evidence for what a blocked waypoint cell does.
3. `code/reinf.cpp:582` and `:616`. `drop_pod` is always false in `Create_Reinforcement`, because `Do_Reinforcements` returns for every `IsDroppod` team first. The branch and its comment ("arriving by drop pod") are dead. Remove after item 1.
4. `code/house.cpp:8578`, naval branch of `Where_To_Place_Building`. It searches from `Center.As_Cell()` while the rest of the function moved to `Starting_Cell_Or_Default()` in `2b88bf11`. Failing case: a house whose start position is set and whose structures are all gone searches for a yard from cell `0,0` instead of its start. Fix: use the starting cell, if gamemd's `0x5060B0` reads it for the water search too.
5. `code/house.cpp:10181`, `Pick_Drop_Target`. `2b88bf11` added `Cell(2, 2)` before `if (cell == CELL_NONE)`. A failed `Nearby_Location` returns `Cell(0, 0)`, so the test is dead and a failed search aims the drop at cell `2,2`. Also found by the buildings review (its finding 1).
6. `code/object.cpp:1669`, with `code/house.cpp:6715` (`Restore_Starting_Buildings`). A `CanC4=no` building clamps `damage < 1` to `1`, which includes a negative (healing) amount. `9ca3ced1` passes `-MaxStrength` unforced, so a standing `CanC4=no` structure takes a point of damage instead of being mended. `code/debugmode.cpp:164` records the same for the restore-health cheat. Fix: clamp only a zero result, if gamemd (`0x5F5390`) does.
7. `code/taction.cpp:2228`, `:3234` and `code/team.cpp:3588` guard a new storm with `LightningStormClass::Is_Active()`, and the Ion Storm stop calls `End()`, which ignores a storm in its deferment (`code/lstorm.h:58`). `LightningStormClass::Start` assigns `Center` and `Owner` (`code/lstorm.cpp:186`) before it checks for a storm that is raging or pending, so a second call during the warning period moves the pending storm. The computer's own call uses `Is_Active_Or_Pending()` (`house.cpp`). Fix: use `Is_Active_Or_Pending()` in the actions, and move the two assignments below the early returns. Whether gamemd does this needs a check.
8. `code/team.cpp:2641`, `:3729`, `:3764`, `:3801`. `BuildingTypes[mission->Data.Type]` is not range checked. A script line with a stale or hostile building number reads outside the vector.
